SEDD — Teknisk granskning: backend

Datum: 2026-05-25
Granskade filer: server.js, db.js, emailService.js, authRoutes.js

1. Syfte och omfattning

Syftet med denna rapport är att dokumentera säkerhets-, stabilitets- och robusthetsbrister i backend-koden för SEDD, ge konkreta rekommendationer och leverera kodförslag (patcher) för högt prioriterade problem. Granskningen täcker autentisering, password reset, databasanslutning, e-post och filimport.

2. Sammanfattning (högnivå)

  • Kritiska problem: dubblett av /reset-password, loggning av reset-token i klartext, db.js som kör process.exit(1) vid DB-fel, och användning av MemoryStore för sessioner i produktion.
  • Praktiska buggar: variabelskugga i diagnoses-endpoint, osäkra SMTP/TLS-inställningar, sync filoperationer utan felhantering, inkonsistenta env-namn.
  • Rekommendation (prioritering): (1) ta bort token-loggning & dubblett-route, (2) säkra DB-anslutning, (3) standardisera e-post/env & TLS, (4) byt session-store i produktion.

3. Viktiga fynd (prioriterade)

3.1 Dubblett: reset-password route

Observation: En POST /reset-password finns både i server.js och i authRoutes.js. Express använder sista registrerade route — det leder till inkonsekvent beteende.

Åtgärd: Centralisera i en fil (rekommenderat: authRoutes.js) och ta bort den andra.

3.2 Token loggas i klartext

Observation: Reset-token loggas (console.log) i authRoutes.js (och i den duplicerade route i server.js).

Risk: Allvarlig säkerhetsrisk — ta bort token-logging omedelbart.

Föreslagen ändring: ersätt token-loggutskrifter med en diskret händelselogg, t.ex.:

// DÅLIGT
console.log(Synlig token: ${resetToken});// BÄTTRE
console.log('Reset token generated for UserID=' + user.UserID);

3.3 db.js: process.exit(1) och brist på error-hantering

Observation: db.js kör process.exit(1) vid connect-fel och saknar pool.on('error'). Pool-/promise-referenser kan bli inkonsistenta.

Åtgärd (kort): ta bort process.exit, kasta felet eller implementera retry/backoff, lägg till pool.on('error') som nollställer pool-variabler, och exponera closePool() för graceful shutdown.

3.4 Session store: MemoryStore i produktion

Observation: express-session använder MemoryStore utan miljöstyrning.

Åtgärd: byt till Redis/SQL-store för produktion (styr via env, t.ex. SESSION_STORE=redis och REDIS_URL).

3.5 E-post: osäkra default-inställningar och env-inkonsekvens

Observation: emailService.js använder secure:false, tls.rejectUnauthorized=false och blandar SMTP_* och EMAIL_* env-namn. sendPasswordResetEmail använder process.env.SMTP_USER som från-adress.

Åtgärd: standardisera env-namn (SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS, EMAIL_FROM, SMTP_SECURE, SMTP_REJECT_UNAUTHORIZED), gör TLS konfigurerbart och defaulta till säkert läge i produktion.

3.6 Filoperationer: sync utan felhantering

Observation: flera ställen använder fs.writeFileSync och fs.unlinkSync utan try/catch.

Åtgärd: använd asynkrona fsPromises eller wrappa unlink i try/catch för att undvika uncaught exceptions som stoppar request.

3.7 Variabelskugga i diagnoses POST

Observation: dubbel deklaration av const { name } i samma scope — detta skulle kasta fel.

Åtgärd: ta bort dupliceringen och gör en enda deklaration.

4. Riskbedömning

  • Säkerhet (Hög): token-loggning och osäkra SMTP/TLS.
  • Tillgänglighet (Hög): db.js som avslutar process vid DB-fel.
  • Integritet/spårbarhet (Medel): logEvent använder process.env.USERNAME istället för session-användare.
  • Drift/skalbarhet (Medel): MemoryStore för sessioner.

5. Testplan (acceptanstester)

  1. Password reset flow: begär reset, kontrollera e-post (testbox), använd länk, verifiera att token i DB är hashad och rensas efter reset, inga tokens i loggar. Testa utgången token.
  2. DB reconnect: simulera DB-avbrott, verifiera att app inte kraschar okontrollerat och återansluter.
  3. Sessions: kör flera instanser med Redis-store och verifiera delade sessioner.
  4. E-post/TLS: kör prod-inställningar (SMTP_SECURE=true) och verifiera felhantering.
  5. File import: ladda upp giltig/ogiltig Excel och kontrollera att temporära filer tas bort samt inga uncaught exceptions.

6.1 Förbättrad db.js (ersätt hela filen)

// db.js — förbättrad poolhantering med eventlistener och env‑konfig
const sql = require('mssql');
require('dotenv').config();const dbConfig = {
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  server: process.env.DB_SERVER,
  database: process.env.DB_DATABASE,
  options: {
    encrypt: process.env.DB_ENCRYPT === 'true',
    trustServerCertificate: process.env.DB_TRUST_SERVER_CERT === 'true'
  },
  connectionTimeout: Number(process.env.DB_CONNECT_TIMEOUT) || 15000,
  requestTimeout: Number(process.env.DB_REQUEST_TIMEOUT) || 300000,
  pool: {
    max: Number(process.env.DB_POOL_MAX) || 10,
    min: Number(process.env.DB_POOL_MIN) || 0,
    idleTimeoutMillis: Number(process.env.DB_POOL_IDLE) || 30000
  }
};let pool = null;
let poolConnectPromise = null;async function createPool() {
  const p = new sql.ConnectionPool(dbConfig);
  p.on('error', (err) => {
    console.error('MSSQL pool error:', err);
    try { p.close().catch(()=>{}); } catch(e){}
    if (pool === p) {
      pool = null;
      poolConnectPromise = null;
    }
  });
  poolConnectPromise = p.connect();
  await poolConnectPromise;
  return p;
}async function getPool() {
  if (!dbConfig.server || !dbConfig.database) {
    throw new Error('DB configuration missing (DB_SERVER/DB_DATABASE)');
  }  if (!pool) {
    try {
      console.log('db.js: connecting to MSSQL...');
      pool = await createPool();
      console.log('db.js: MSSQL pool ready');
    } catch (err) {
      console.error('db.js: initial DB connect failed:', err);
      pool = null;
      poolConnectPromise = null;
      throw err;
    }
  }  if (poolConnectPromise) {
    await poolConnectPromise;
  }  return pool;
}async function closePool() {
  if (pool) {
    try { await pool.close(); } catch (e) {}
    pool = null;
    poolConnectPromise = null;
  }
}module.exports = { getPool, closePool, sql };
